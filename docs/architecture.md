# Architecture

Fell is a native Proton Mail client. The UI never talks to the network; it reads a local store that a sync layer fills from a mail backend.

```text
┌─────────────┐     ┌─────────────┐     ┌──────────────────┐
│  fell (GPUI)│     │   fell-mcp  │     │ Proton Mail      │
│  Wayland UI │     │  scoped MCP │     │ Bridge (IMAP)    │
└──────┬──────┘     └──────┬──────┘     └────────┬─────────┘
       │  types only       │  search/draft       │ later: Proton API
       ▼                   ▼                     ▼
┌─────────────────────────────────────────────────────────┐
│                      fell-core                          │
│  accounts · backend trait · sync · sqlite+fts · threads │
└─────────────────────────────────────────────────────────┘
```

## Crates

| Crate | Role |
| --- | --- |
| `fell-core` | Accounts, backend trait, sync, local SQLite store (FTS5 and a local body-embedding index), threading, search, send-confirmation types. No UI. |
| `fell-render` | Styled document shared by received HTML and later markdown compose. Chooses native vs web view. No GPUI. |
| `fell-confirm` | Sealed `InteractiveUi` (private field, not `Default`). Required to mint a send confirmation. The GPUI app depends on it; `fell-mcp` must not. |
| `fell` | GPUI application. Opens a Wayland window and paints one message with `fell::render::MessageBody`. Does not own the thread list, keymap, or command palette. Depends on `fell-core` for data, not the other way around. Mints send confirmations. |
| `fell-mcp` | Stdio MCP server. Search, read threads, list labels, triage, and review drafts. No send tool. Scopes stay off until enabled. |

## Backends

`MailBackend` is the seam.

1. **Bridge** — Proton Mail Bridge over local IMAP, plus SMTP submission on `smtp_host`:`smtp_port` (default `127.0.0.1:1025` with STARTTLS) using the same username and password. The login, password source, and SMTP settings come from `~/.config/fell/account.toml` for the draft's account id. By default setup stores the password in the desktop Secret Service and records `password_source = "keyring"`. Inline `password` and `password_command` are also supported. `smtp_security` defaults to `starttls`, which refuses a server that does not offer STARTTLS rather than log in over cleartext. `"plain"` must be set explicitly and is only allowed for a literal loopback address, like IMAP's `security`. `fell account setup` and `fell account check` (`AccountConfig::check_smtp`) log in to that server with `EHLO`, `STARTTLS` when required, `AUTH`, and `QUIT`, never `MAIL FROM`, and classify failures like an IMAP login. Bridge stays a separate process. The message is `pending.mime`. Bcc is an envelope recipient only, and the socket that carries a message opens only from `confirm_send` after the editor's send confirmation matches. The setup and check socket is login-only.
2. **IMAP** — any other IMAP account. Uses the same SMTP submission path as Bridge. The SMTP host defaults to the IMAP host, with port 465 for TLS or 587 for STARTTLS. Override the host, port or security in the account file.
3. **Proton API** — direct Proton HTTP API. Same trait, not implemented.

Sync logs in, lists mailboxes, and `EXAMINE`s each one (read-only). The listing also says what each folder is for; see Folder roles. New mail is `UID FETCH` with `BODY.PEEK`, so the server is not asked to mark mail read. A cursor stores UIDVALIDITY, the highest UID, and HIGHESTMODSEQ when the server advertises CONDSTORE. The next sync fetches only newer UIDs, or `CHANGEDSINCE` when a modseq is known. A `CHANGEDSINCE` pass asks for flags only (`UID FLAGS`) and then fetches bodies by UID for what the store has no copy of, so a flag change made elsewhere (read on the phone, a Proton label) updates unread without downloading the message again. A high-water pass whose checkpoint sits below stored mail goes the same way, so a known UIDVALIDITY and UID is never downloaded twice. A flag change reaches the row through whichever copy reported it (INBOX or Sent, INBOX or All Mail), not only the copy the row was last written from. For a row emptied from Trash in Fell, it is written on the snapshot undo restores. A copy with neither row nor snapshot is fetched again like new mail. A body fetch that ends without a UID it asked for keeps the checkpoint below that UID. A mailbox's first sync (no checkpoint, or a new UIDVALIDITY) reads it newest first, so a new account shows today's mail within moments of login. It walks down from `UIDNEXT - 1` in windows of 500 messages (100 for the first); a window's lowest UID is the UID at the sequence number one window below the last, so windows hold about as many messages however sparse the UIDs are. Each window fetches `UID FLAGS RFC822.SIZE BODY.PEEK[HEADER]` first and stores rows with no snippet or body, then the bodies, newest first, about 50 to a `UID FETCH`, each batch written as it arrives; the snippet fills in on a row whose height does not change. A UID search verifies each header window so a FETCH that omits an existing message leaves the window pending. The cursor's floor moves below each fetch of bodies in the same write, so a restart resumes below what was read. A pass reads the newest 2,000 Inbox messages, then the newest 1,000 of the Sent folder (by role) so replies thread, then the rest of the Inbox, then the newest 1,000 of each other folder (All Mail, Trash and Junk last), then everything older. A copy whose message already has a body from another folder is not downloaded again. A copy counts as stored only once its row has a body, so a row left with only its headers gets its body on a later pass. A body larger than sync keeps (32 MB) leaves its header row marked so (`message_bodies.withheld`), in the write that moves the floor below it; it is not asked for again, the conversation says "Too large to download", and `fell-mcp`'s `read_thread` gives `body: null` with `body_too_large`. A row still waiting for its body reads "Not downloaded yet" and has `body_pending` in `read_thread`; the open conversation fills it in place, fading in, when it comes. Flag changes and removals in a mailbox being walked wait until the walk reaches its oldest message; it is then listed as at the end of a full first pass, and the modseq recorded when the walk began has the next pass ask `CHANGEDSINCE` for every flag changed since. A server without CONDSTORE has its flags read in bounded UID batches. An incomplete flag sweep keeps the walk open for the next pass without downloading the completed windows again. A mailbox whose UIDVALIDITY changes between two visits of one pass starts over. When no folder has the Sent role, the name table's Sent mailbox gets the early visit. The status bar counts completed messages (`syncing Inbox · 4,210 of 31,882`). A header-only row is visible while its body is still pending in that count. A server that omits UIDNEXT is read oldest first, as before. Between passes the sync thread waits on INBOX with IDLE (RFC 2177) on a read-only `EXAMINE`, so new mail starts a pass within moments. A full pass still runs at least every 60 seconds to catch up other folders. Mail that arrived after the last pass but before IDLE began counts as news, so nothing waits out the interval. A server without IDLE falls back to the 60-second timer. Each pass also notices mail that left a mailbox (deleted, or moved, in Proton web or another client). With QRESYNC the `CHANGEDSINCE` fetch asks for `VANISHED`. That stands in for a listing only when the UIDs it names account for the drop in EXISTS; a set with `*` (the highest UID, which may still be there) is not applied at all. Otherwise the mailbox is listed with `UID SEARCH` in pages of 5,000 by sequence number, and the listing counts only when no expunge arrived while it ran and it holds one ascending UID per message `EXAMINE` counted. The cursor keeps EXISTS and UIDNEXT from the last full listing; when both still match, nothing was added or removed and no listing is sent. The store records every server copy behind a row (mailbox, UIDVALIDITY, UID), including copies merged by Message-ID or by fingerprint. A vanished UID drops only that copy. At the end of the pass a folder comes off a row once no copy of the row is left in it, and a row with no folder and no copy left is deleted with its search postings, body vector, queue entry, and aliases. A server move adds the new copy during the same pass, so the row and its local state stay. If some mailbox could not be read that pass, rows that would be deleted wait, since their copy may have moved there. A UIDVALIDITY change refetches that mailbox, then lists it with Message-ID headers (the body fetch skips mail flagged `\Deleted` or too large) and records every copy still there before copies under the old value are dropped. An old copy whose row has no new copy stays while its UID is still taken. A message with no Message-ID gets a new id under the new UIDVALIDITY; the new row takes the old row's labels, star, archive bit, and snooze when sender, subject, date, and body match. Mail synced before copies were recorded has one copy per row. The first listing of each mailbox therefore fetches Message-ID headers (`BODY.PEEK[HEADER.FIELDS (MESSAGE-ID)]`), records the copies it finds, and takes that folder off rows that list it with no copy there, unless a local action touched the row. The sync session has no send command, no write command, and no OAuth. Bridge SMTP is a separate socket. Write-back has its own session; see Write-back.

On generic IMAP accounts, each complete FLAGS reply updates the keywords recorded for that copy. Sync adds those keywords as labels, except reserved IMAP keywords (the IANA registry names such as `$Forwarded` and `$MDNSent`, plus client flags such as `Junk` and `NonJunk`), which stay on the copy and never become labels. It drops a label it introduced when the last copy stops reporting it. Labels added in Fell and labels from before the store recorded keyword provenance are kept. Bridge labels continue to follow mailbox membership. Servers without CONDSTORE can report keywords when sync fetches flags, such as during a first-sync sweep. Their steady-state UID high-water pass does not poll old flags.

The UI and MCP crates take `dyn MailBackend` (or a store already populated by sync). They do not import IMAP or Proton protocol code.

## Local store

SQLite is the source of truth for the UI. Sync writes messages, threads, and an FTS5 index. Reads do not block on the network. If Bridge or the API is down, the last synced mailbox still renders.

The window, sync, compose, and the indexer each write on their own connection, and SQLite lets one write at a time. Every write transaction takes the lock at `BEGIN IMMEDIATE`, before it reads, so waiting for the lock is safe (a deferred transaction that read first could not wait and failed at once; compose drafts did that). A store connection that finds the lock taken tries again every few milliseconds for up to 30 seconds, not every 100 ms for 5 seconds. While a write other than sync's is waiting, its connection notes the time in memory that every store this process has open on the same file shares (keyed by the file's inode), and sync lets that write go first before its next batch: sync commits batches back to back while the server streams, and archive, undo, or a draft save used to lose that race and fail with "database is locked". The end of a mailbox can carry a flag and a found copy for every message. Sync looks them up through indexes on `remote_id` and by row (one walk of the account each used to make that delta take about 20 minutes on 50,000 messages). A large delta is two transactions, with a turn for waiting writes between them: its new messages and every flag, then every found copy, the copies its listings no longer show, settling, and the cursor. Neither is cut inside. A read or unread change that lands between them comes after every flag, and an action reading the copies never sees half a listing. The cursor lands in the second, so a pass cut short is redone by the next. On 50,000 messages each takes about a second, and a user write that arrives meanwhile waits for it. Another process (`fell-mcp`) gets the same 30-second wait but not the turn.

Each IMAP mailbox is one folder on the message. A message with no Message-ID is stored under a stable id from the mailbox, UIDVALIDITY, and UID. Copies with the same Message-ID stay one row; see Threading.

## Folder and label lists

A folder list reads `thread_summary` (one row per thread: first subject, latest snippet and sender, participants, labels, star and attachment markers, message count) joined to `thread_folders` (one row per thread and folder, with that folder's unread state). It does not read `messages`, so its cost follows the folder, not the mailbox. `account_folders` keeps each folder name's earliest stored spelling for the picker.

Triggers on `messages` queue every thread a write touches in `thread_summary_dirty`, whatever code made the write. Every write transaction (`WriteTx`, from `immediate_transaction`) recomputes its queued threads from their messages before it commits, so a reader sees summaries that match the messages they came from. A reader treats a thread still in the queue (a write that bypassed `WriteTx`) as unknown and computes it from `messages`, so the list is right either way. The first open of an older mailbox queues and fills every thread once. A randomized test checks folder lists and folder names against a scan of every message after archive, move, label, delete, undo, and flag changes.

A folder list is read a window at a time, near the reader. `Store::folder_page` takes a `FolderSpan`: the top or bottom rows, or a run between two list positions plus some rows on either side. A position is a `ListKey`, the `(last date, thread id)` that orders the list, so rows sync adds elsewhere never shift a window the way an offset would. `thread_folders` carries the thread's last date, and an index in list order lets each read seek to its first row and stop after its last. The same read returns whether the folder has rows beyond either edge, and an unread count from a partial index of unread rows, so the header counts the whole folder. Each refresh rereads the loaded rows plus whatever the list asked for: more rows near an edge the cursor or the viewport approaches, the bottom for `G`, the top for `gg`, or the rows around a thread undo brings back. Rows far from the cursor, the visual anchor, and the viewport are dropped.

Label lists use the same paging over `thread_labels`, which indexes exact label tokens in list order and counts a conversation as unread if any of its messages are unread. The summary refresh maintains the index, and the first open of an older store backfills it from its summaries. The picker seeks from one label name to the next in the index and also includes labels from Bridge's mailbox listing.

## Folder roles

Sync records which folder is Inbox, Sent, Drafts, Trash, Junk, Archive, All Mail, and Flagged for each account (`folder_roles`, read with `Store::folder_roles`). A server that advertises SPECIAL-USE (RFC 6154) is listed with `LIST "" "*" RETURN (SPECIAL-USE)`; a plain `LIST` follows when it refuses that option. The attributes (`\Sent`, `\Trash`, and the rest, plus the older XLIST spellings `\AllMail`, `\Spam`, `\Starred`) are read from whichever reply arrives, since some servers mark folders on a plain `LIST` without advertising SPECIAL-USE. Only when the server marks no folder at all does `FolderRole::fallback_names` match names (`Sent Items`, `Deleted Messages`, `Junk`, and so on, also directly under `INBOX`). `sent_folder`, `drafts_folder`, `trash_folder`, `junk_folder`, `archive_folder`, `all_mail_folder`, and `flagged_folder` in `account.toml` win over both. The map is written in its own delta right after the listing, so the first pass already knows it, and each later listing replaces it. An account no server has listed (the demo mailbox, or mail stored before this table existed) reads the name table over its stored folder names; a role still missing uses the table's first name.

Each entry keeps the decoded name messages are stored under and the server's raw (modified UTF-7) name for IMAP commands. Archive, delete, `gi`/`gs`/`gd`, and the folder picker ask for a role, not a spelling. The window shows the role's label ("Sent", "Spam", "All Mail") for that folder and the server's name for every other folder.

## Search

`Store::search` reads that store and nothing else. It does not call a backend, so results move only when a local write does.

The query language is FTS5 BM25 plus operators: `from:`, `to:`, `subject:`, `in:`, `label:`, `has:attachment`, `is:unread`, `before:`, and `after:`. `from:`, `to:`, and `subject:` are FTS column filters (`to:` covers To, Cc, and Bcc). Folder, label, attachment, unread, and date operators filter the message row. Every operator on one query applies to the same message. Hits are then grouped to one row per thread, ordered by that message's BM25 score (subject weighted above sender, recipients, and body). A query that is only operators still runs.

Misspellings use a character-trigram index of words from subject, sender, recipients, body, folders, and labels. Damerau-Levenshtein confirms a candidate. When the typed query matches nothing and the corrected query matches, the response carries those hits and `did_you_mean`. Keyword search does not read the local embedding index.

## Local embeddings

Each message body has one row in `message_embeddings` in the mailbox SQLite file (the same `mail.db` the account's messages already use), keyed by account id and message id. Deleting that file deletes the index. Deleting a message deletes its row in that transaction. A body change drops a stale row. The row stores a model id, a model version, and a little-endian `f32` blob.

The embedder is the `BodyEmbedder` trait. Which one fills the index depends on what is on disk:

- By default it is `local-hash-v1` version `1`, a placeholder lexical feature hash of `body_text` (or the snippet when the body is null). It is not a semantic model and has no weights.
- After `fell embeddings install`, it is `all-MiniLM-L6-v2-qint8` version `1`: the int8 ONNX export of [`sentence-transformers/all-MiniLM-L6-v2`](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) (Apache-2.0), run with `tract-onnx` (pure Rust, MIT OR Apache-2.0). It produces 384 dimensions: BERT uncased WordPiece, truncated at 256 pieces, mean-pooled and L2-normalised, as the model card describes.

Fell does not download weights at first launch, when it opens the mailbox, or while it indexes. `fell embeddings install` is the only download. It prints both URLs (pinned to one Hugging Face commit), their sizes and SHA-256, the license, and the destination, then asks first; without a terminal it needs `--yes`. Files are written to an owner-only staging directory (0700, files 0600) under `$FELL_MODEL_DIR`, else `$XDG_DATA_HOME/fell/models`, else `~/.local/share/fell/models`. Directories are created without following symlinks; an existing one must be a real directory owned by the user, and its mode is set through a no-follow descriptor. They are renamed into place only when every size and hash matches. An old install that failed its check is renamed aside first and put back if the new one cannot be renamed in. Staging copies an interrupted install left behind are removed by the next install. `fell-core` links no HTTP client: the install takes a fetcher, and only the `fell` binary passes one (ureq over rustls with the system trust store). `fell embeddings status` loads the model the same way the indexer does and reports what the indexer will run. Each download has a five-minute deadline. `fell embeddings remove` deletes the files.

The indexer thread looks for the installed files when it starts, re-hashes them, and loads them. That takes about 350 ms on an M2, off the opening thread. Each file is opened without following symlinks and must be a regular file; it is hashed and loaded from that one descriptor. A missing, symlinked, or mismatched file keeps `local-hash-v1`. Files that are present and match but cannot be read or do not load (tract rejects the graph) are not a switch to `local-hash-v1`: the indexer writes nothing, logs the error, and retries the load with a backoff up to 15 minutes, and again on the next open. When the model fails on one message, no row is stored for it. The message stays queued and is retried, up to three times for the same body and model; a new body or another model starts the count again. A body with no word pieces is the zero vector. Rows whose model id, version, dims, or vector length differ from the active embedder are rewritten in the usual batches. Installing or removing the model therefore rewrites the whole index in the background, the next time a mailbox is opened. On an M2, one core, the int8 model embeds a 256-piece body in about 100 ms. A full rewrite of 500 mixed messages took about 25 s. A body edit drops its row. A resync with an unchanged body keeps the row, whatever model wrote it, and leaves model changes to the indexer.

`Store::open` starts a background thread that fills missing or outdated rows, recent mail first, after taking an exclusive lock on a sidecar of the mailbox path actually opened. Once a path is recorded on the file, every open uses that path and does not replace it or checkpoint a second name. A symlink open does not touch that name when the canonical `-wal` already has frames. An alias `-wal` is replayed only when the canonical `-wal` is absent, and only before the canonical path is opened. Keeping a non-canonical path fails the open when that path cannot be recorded, so a later open does not guess the canonical file while another store is still using the other name. The path is chosen only while this process alone holds the exclusive lock. Every live store then holds a shared lock, so a later open cannot start a second WAL. A second opener waits until that shared lock is available, not for a fixed interval. If the filesystem cannot store the path or the lock, and this is the only name for the file, the canonical file still opens. Closing the store stops the worker between messages and wakes it out of a lock wait. If that lock cannot be created, the mailbox still opens. A process that finds the lock held keeps trying and starts indexing when the lock is free, so closing the other mailbox does not leave the queue unindexed. The worker drops the lock when it stops. Hashing happens before the write transaction; the transaction only stores rows whose body is still the one that was hashed. A second process does not index while the lock is held. New and invalidated messages are queued and indexed before the historical walk. A pass walks from newest to oldest and resumes after the last row it stored. Mail newer than that floor is paged until a short batch shows the range is done, so a sync burst is not skipped. Each batch is one immediate transaction, then the thread yields so sync and `fell-mcp` can write. Message saves, deletes, and triage also take the write lock at the start of their transaction, so a batch commit cannot invalidate a snapshot they already read. When a pass finds nothing, the thread waits at least a second and backs off. A lock conflict retries after a short fixed delay and does not extend that wait. Open and listing threads do not compute vectors. Nothing leaves the machine. There is no cloud embedder.

### Hybrid search

`Store::search` is hybrid when the model is installed and keyword search otherwise. It embeds the query only with the real model. The `local-hash-v1` placeholder is lexical, so with it, or with no model files at all, nothing is embedded or loaded and the results are exactly the keyword results. `Store::search_with(.., SearchOptions { semantic: false })` is keyword search with the model installed too.

With the model, the free words of the query (operators removed) are embedded on the calling thread. That takes about 3 ms for a short query in a release build on this aarch64 machine. The vectors the indexer stored for that model are held in memory as one packed int8 matrix: per row, one signed byte per dimension, an `f32` scale, and the message key. A query is a brute-force integer dot product over the account's rows. Rows below cosine 0.3 are dropped, and the best 300 messages are kept and grouped into at most 50 threads. When the query has operators, the same filters run in SQL first, and only the rows of messages that pass them are scanned. The keyword thread ranking and the semantic one are merged by reciprocal rank fusion (k = 60). A thread on both lists keeps its keyword hit. A thread only the vectors found has `SearchHit::semantic_only` set, and the UI marks it "related". `did_you_mean` still comes from the keyword side. When it is set, the semantic side embeds and filters the corrected query too, so both lists are for the same words. The whole search reads one SQLite snapshot: a deferred read transaction runs from the matrix refresh through the keyword query, the operator query, the scan and the hit lookup, so a sync or indexer commit in between cannot pair one state's vectors with another's rows. The hit lookup applies the operators again as well.

The matrix is loaded once per store, in one read transaction, on the first hybrid search or earlier on a background thread with its own read-only connection (`Store::warm_search`). The app's store thread calls it when it opens the mailbox file, and so does `fell-mcp serve` when its session starts. After that it follows the index through `embedding_changes`. Triggers on `message_embeddings` append the key of every inserted, updated, or deleted row, so a vector the indexer writes in another process is seen too. Each search applies the entries past the last one it read, in one snapshot. The indexer trims the log to the newest 8,192 entries in its own batch transaction. A store that fell further behind loads the matrix again. Search only reads, and in WAL mode a read does not wait for the indexer or sync. A model that is installed but does not load leaves search keyword-only, and the load is tried again a minute later.

At 100k messages (384 dimensions) the matrix is 38.8 MB, plus 8.3 MB of ids and lookup. Measured with `measure_hybrid_search_at_100k_messages` (ignored by default, see its doc comment): hybrid search including query embedding took p50 10 ms and p95 47 ms over 100 queries (keyword only: p50 1.4 ms, p95 31 ms). The store held real MiniLM vectors of 400 base bodies plus noise.

`fell-mcp`'s `search` takes `mode`: `keyword` or `hybrid`. The default is hybrid when the model loads and keyword otherwise, and the response says which ran. Keyword mode is the same message-level paging as before. Hybrid hits are the fused thread list, 20 per page, each with `related`, and the response carries `did_you_mean` when the query was corrected. Snippets stay in the `untrusted_email_content` envelope.

## Local actions

Archive, move, label, delete, spam, read, star, and undo update this SQLite file. With write-back on, the same transaction also queues server moves, label edits, and read or star changes.

The thread is the unit. Archive moves the folder the caller names (the folder on screen) to the account's archive folder on each message in the thread that has it: the Archive role, or All Mail on a server with no Archive (Gmail). Move does the same to the folder the caller names. Any other folder on that row, such as Sent, stays. Delete (`Store::delete_threads`) moves that folder to the account's Trash. Spam (`Store::spam_threads`) moves it to the Junk role folder; from Junk it moves to the inbox instead (not spam). Both take every thread of a selection as one undo entry. A permanent delete (`Store::purge_threads`) removes the Trash copy from Fell and removes the row when Trash was its last folder. The server copy stays in Trash. A local tombstone prevents sync from restoring that copy. The purge keeps no undo snapshot and retires earlier snapshots for the affected messages. Undo still restores unaffected messages from earlier actions, including the other members of a batch. Labels are a separate list. Reversible actions store the previous folders and labels on the account's undo stack. `Store::undo` restores the latest available entry for that account.

`in:` and `label:` read the columns those calls write. Folder and label words enter and leave the trigram vocabulary with the change. `apply_delta` still unions other folders and labels for the same Message-ID, and leaves out a folder archive or delete removed. Undo restores that folder and then drops the saved message copy, including the body and BCC.

## Write-back

Off by default. `write_back = true` in `account.toml` turns it on for the account; the window records the setting when it opens the mailbox (`Store::set_write_back`). Turning it off starts a new write-back generation and deletes rows never sent. No row from an earlier generation is ever sent or reversed, even after write-back is turned on again, and a reply to a command that was on the wire when it went off changes nothing.

Write-back moves mail with `UID MOVE` (RFC 6851). On a server without MOVE, archive and move stay in Fell and the status bar says so once ("This server can't move mail; archive stays in Fell"). The status bar shows one notice per pass and includes both move and flag failures when both occur. A once-only notice counts as said when it appears on that line, so a half-done copy from an earlier build waits for a pass with nothing else to say. Earlier builds copied, flagged `\Deleted`, and expunged on servers without MOVE. Fell abandons those half-done moves (`copied`) on opening the outbox, and reports them once.

Archive and move write one `server_outbox` row per server copy they moved, in the `WriteTx` that changed the rows: each copy `message_copies` records for the message in the folder being left (mailbox, UIDVALIDITY, UID), and the target's raw name from the folder roles or a recorded copy. Sent copies in Sent are not in that folder, so they stay. When the latest queued move for a message goes into the folder being left and has not reached the server, the copy it will place is not recorded there yet. One more row follows that move, besides the rows for copies already in the folder. It has no UID and is filled in at replay from `message_copies`, which each sent move updates, taking the newest copy no other row moves. A store error while queueing fails the action, so the local change rolls back with it. Delete to Trash, spam, and not spam are moves and queue the same rows. Permanent delete stays local.

The sync thread replays the outbox before each pass, and as soon as the window queues something, on its own connection: a `WriteSession` that sends `SELECT`, never the read-only `EXAMINE` session sync reads with. It logs in only when a row is due. For each source mailbox it checks UIDVALIDITY against the row's; a change means the UIDs name other messages now, so the row is dropped, never applied, and the status bar says so once. Moves are one `UID MOVE` per source and target. A refusal is retried with backoff (10 s to 30 min) and dropped after five; a dropped connection ends the pass and costs nothing. Moves for one message keep their queue order because an earlier move can change the UID a later write needs.

Before a row's first `UID MOVE`, replay reads the target's UIDVALIDITY and UIDNEXT with `STATUS` and marks the row sent, recording both, in one transaction that touches only rows still pending in the current generation; a row undo or the off switch retired after the pass loaded it is not sent. Each row is settled in its own transaction after the server answers, so a restart replays only what was not settled. A NO or BAD to the move clears the sent mark. A missing COPYUID is never taken as "moved, place unknown": a lost reply, or a server without UIDPLUS, leaves the new UID unknown, and a resent `UID MOVE` then finds nothing to move. Replay looks for the message in the target with `UID SEARCH HEADER Message-ID`, which matches substrings and ignores case, so it keeps only UIDs at or above the recorded UIDNEXT under the same UIDVALIDITY, fetches their `Message-ID` headers (`BODY.PEEK[HEADER.FIELDS (MESSAGE-ID)]`), and takes the lowest whose parsed Message-ID is exactly the row's and that no other row moves. A refused search, no match, or mail with no Message-ID leaves the row to retry, and after five tries it is dropped with a notice. A move is recorded as done only with its new UID, so `message_copies` keeps the source copy until a new one replaces it.

Undo of a move deletes its rows that were not sent. For each row the server applied it queues the reverse move from where the message went. A row marked sent but not settled (its reply was lost, or its new copy is still being looked for) stays, and undo queues a reverse with no UID that names it (`reverses`). Rows for one message replay in order, so the reverse waits until that row is done, then moves the copy it placed. If the server refuses that row with NO or BAD, it never moved the message, and both rows are dropped without a notice. If it is given up, the reverse is dropped quietly too. While a reverse, or any other unsettled row, moves a message into a folder, sync does not take that folder off the row. Undo has already put the row back and cleared its tombstone, and a pass that read the server before the reverse was sent sees the copy only where the action moved it. A sent move also queues the folder its source copy backed, as sync does for a copy it sees go, so a folder a pass added in the meantime comes off once no copy is left there. Sent and dropped rows are kept for 30 days.

Read, unread, and star (`Store::flag_threads`) take a list of threads and are one undo entry for all of them. Read clears every message in the thread. Unread and star go on the thread's latest message in the folder on screen, so the row changes there and reopening expands only that message. Unstar clears every message. These entries save only the read and star state of the messages they changed, not whole rows. A call that changes nothing, such as opening a thread that is already read, logs nothing.

Each read or star change from the reader, agent triage, or undo records a local intent. With write-back enabled, it also queues the final value for each copy in `message_copies`. A subsequent edit to the same flag replaces the unsent rows. MOVE retargets pending flag rows to the new copy. A refused STORE backs off independently while moves and writes to other copies proceed. A STORE whose outcome is still unknown holds further writes to that copy, including a move that would change its UID. If recovery of an older STORE delays a newer edit for five attempts, the status bar reports the delay while recovery continues. The worker sends `UID STORE +FLAGS.SILENT` or `-FLAGS.SILENT` for `\Seen` and `\Flagged`. Proton Bridge maps `\Flagged` to a Proton star.

With CONDSTORE, each queued read or star write snapshots the copy's last observed MODSEQ and the targeted flag's value there. Replay reads both bits in one `UID FETCH` when it needs a baseline, receives `MODIFIED`, or needs to confirm a previous attempt. It records the observation and settles or rebases pending writes in one transaction. A `MODIFIED` with the target still at its known baseline retries against the learned revision. A newer revision with a mismatching target and no known baseline takes the server value conservatively. The remaining writes for a conflicting intent are retired, and Fell shows unread if any observed live copy is unread and starred if any observed live copy is flagged. This includes copies that already accepted the write and copies whose writes were retired. A newer local edit retains its own value and queue entries. Without CONDSTORE or on a mailbox that returns `NOMODSEQ`, plain STORE can set or clear only the requested flag and cannot detect concurrent server edits.

Label edits are one action for a thread or selection. With write-back off, Fell keeps them in the local store. Turning write-back on queues only new edits. Labels applied while it was off stay local. With it on, Bridge copies into the `Labels/<name>` mailbox, creating the mailbox if needed. Removal selects only that label mailbox, checks UIDVALIDITY and uses `UID EXPUNGE` on the specific copy. A lost COPY reply is recovered using the target UID bound and exact Message-ID, using the same recovery as a move. Bridge quotes the modified UTF-7 mailbox name and keeps names with relative path components local. Generic IMAP fetches each recorded copy’s keyword state and changes only the requested keyword with incremental STORE. Names outside the IMAP keyword grammar stay local. An edit made before the first copy is recorded queues a write that waits for server copies. When they arrive, replay expands a deferred keyword edit to one row per recorded copy at the edit's original queue position. Gmail label write-back is separate. Undo cancels unsent writes and reverses applied writes through the outbox. Sync records copy observations while those writes are pending, and leaves the local label value in place until replay settles. MCP label edits take the same path through the agent’s triage log.

## Threading

A thread id is assigned when a message is stored, then the rows that write touched are re-resolved from threading columns (not bodies):

1. If Proton sent a conversation id, that is the thread key (`proton:…`).
2. Otherwise join via `In-Reply-To` / `References` to an already-stored parent in the **same account**.
3. Otherwise, for a reply whose sender dropped `In-Reply-To` and `References`, join by subject (below).
4. Otherwise start a thread from the message's own `Message-ID`.

**Replies without threading headers.** A message with no Proton conversation id and no `In-Reply-To` or `References` at all (one that names a parent waits for that parent, because a join is never undone), whose subject reads as a reply or forward (`Re:`, `RE[2]:`, `AW:`, `SV:`, `Fwd:`, `回复：` and others), joins the latest earlier message with the same subject once the markers and list tags are stripped and case and spacing are folded. Two conditions must also hold: each sender is among the other message's sender, To, and Cc (when both share a sender, they must also share someone else), and the original is at most 30 days older. A bracket tag with a digit (`[PROJ-12]`) stays part of the subject, so different tickets stay apart. Subjects that are short or stock (`Hi`, `Thanks`, `Meeting`, `Invoice`…) never join. `subject_index` lists the stripped subjects. When a message arrives, changes, or is deleted, the pass also re-checks later replies in its window, so the join works whichever copy syncs first. Headers and Proton ids always win over a subject.

Messages are unique on `(account_id, message_id)`. A second copy with the same id (a Sent copy, or the same message delivered to several aliases) stays one row and unions folders, labels, arrival addresses, and recipients, and keeps an attachment if either copy had one. A different Message-ID collapses only when the body fingerprint is exactly the same, the sender is the same, both dates are non-zero and within six hours, at least one copy has `List-Id`, and the Proton conversation ids are absent or equal. The fingerprint is only of non-empty body text. A missing body has no fingerprint, and subject is not an identity. More than one matching row stays as separate messages. A row that already remembers another Message-ID is not a collapse target for a later message. The merge keeps every body, parent, subject, proton id, folder, label, address, star, archive bit, and snooze already stored, prefers the non-list subject, display name, and `In-Reply-To`, and copies a proton conversation id onto a row that lacks one. An upgrade joins duplicate fingerprints in batches, without loading every body at once. A pair stored before `list_id` existed joins only when one copy is in Sent and the other subject has a list tag for that same subject. Two plain messages with the same body stay apart. The account is rethreaded before schema version 3 is stamped so a reply to a deleted copy stays with the surviving row. Later mail still needs a list id on one side. A same-id resync replaces `In-Reply-To` and `References` when the incoming copy has them. When that resync is not a list rewrite of a row that already absorbed the other copy, a non-empty incoming subject, display name, and Proton conversation id replace the stored ones. An empty incoming Proton id still keeps the stored one. A later sync of the list copy does not wipe a body, parent, subject, or Proton id the other copy filled in. The other Message-ID is remembered so a reply to it still joins the row.

After a delta with messages is written, each row's previous thread and its header-parent thread are unioned. A `proton:` id absorbs a non-proton header thread. Two different `proton:` ids are not unioned. Non-proton merges keep the earliest already-assigned thread id, so the first id handed back still lists the messages after a missing parent arrives. Cursor-only deltas skip the pass.

The pass is incremental. Triggers queue every inserted or re-parented row (`thread_dirty_rows`) and every Message-ID that came or went, such as a deleted row or a new alias (`thread_dirty_ids`). `message_refs` indexes each row's `In-Reply-To` and `References` ids, so a parent that arrives late finds the replies that name it without a scan. The pass resolves the queued rows and those replies, in row order, with the same union rules, and clears that account's queue. A batch costs the same at 1k and 100k stored messages. Deletes and undo only queue; the next delta resolves them. The first open of an older mailbox fills `message_refs` and runs one whole-account pass, so every untouched row starts on its final thread. A randomized test checks every step against the whole-account pass. A thread-id-only update does not rewrite FTS (the update trigger is `OF` subject, from name, from email, body, snippet, and the recipient columns). A delta whose rows belong to another account is rejected and does not advance the cursor.

Proton conversation ids are preferred so Bridge and the future API stay consistent with Proton's own threading, and two Proton conversations stay two threads. Sync applies a mailbox delta in one SQLite transaction (messages, rethread, cursor).

## Sending mail

Agents may prepare a `Draft`. Each `submit_draft` mints a unique pending id. Transmitting mail requires a `UserSendConfirmation` minted with `fell_confirm::InteractiveUi::for_fell_app` (see `fell::confirmation_from_ui`) and bound to that id plus the account, recipients, subject, body, reply parent (`in_reply_to`), attachments, and a SHA-256 of the exact MIME bytes that were shown. `ImapBackend` and `BridgeBackend` both check that token before submitting the pending MIME over SMTP. A failure while the message body is still being written leaves the draft available to retry. A failure when writing the terminating dot, or a missing or unexpected final reply, is `Error::SendUncertain`. An explicit server rejection leaves the draft editable. The editor records the send claim before it starts and keeps the draft locked if the message was or may have been sent. The lock survives reopening and restarting. Bcc recipients are `RCPT TO` and are not a header of the message. A token for draft A does not confirm draft B. `InteractiveUi` is sealed (private field, not `Default`) so a crate that only depends on `fell-core` cannot mint it. The MCP crate has no send tool and does not depend on `fell-confirm`.

An agent draft is a `review_drafts` row (`Store::list_review_drafts`), not a `PendingSend`. Fell reads that list when it is time to show the draft for review. Undo deletes it. `create_review_draft` never calls `submit_draft` or `confirm_send`.

Triage (label, archive, mark read, snooze) writes an `agent_actions` row and the previous message state. `Store::undo` reverses the latest action on the account, including ones an agent took. `Store::undo_actor` reverses only that actor's latest action. Archive and snooze survive a later copy of the same Message-ID.

Per-agent scopes live in `agent_grants` and are off until `fell-mcp grant` (or a later UI) enables them. `read` covers search, reading a thread, and listing labels. `triage` covers the four triage tools and undo of those, and stays off unless that scope is granted. `draft` covers saving and listing review drafts and undo of those. A disabled agent gets an empty tool list. Mailbox changes are rate-limited.

`fell-mcp` speaks MCP on stdio only. It does not listen on a socket. Draft tools (`get_draft`, `edit_draft`, `replace_draft_body`, `request_send`) connect to the compose window's unix socket when Fell is open, so the agent reads the text on screen. That socket is mode `0600` under the user runtime directory. It is not a network listener. `request_send` only focuses the editor. Any future network transport must bind to `127.0.0.1`, authenticate with a token file created mode `0600`, and check the `Origin` header.

Search returns at most 20 hits per page: ids, sender address, date, and a short snippet. Thread bodies are plain text and truncated. Draft bodies are capped when they are saved. Text that came from mail is returned only as `untrusted_email_content`, with ids, sender address, and date outside that object. The model is told to treat that text as data, not as instructions. `list_drafts` defaults to the calling agent's drafts and redacts `bcc` on anyone else's rows. The database file, its WAL file, and its shared-memory file are mode `0600`. See [agents.md](agents.md).

The in-app action log, one-key undo, and an in-app confirm for bulk archive are not part of this server.

## HTML mail

`fell-render` turns HTML into a `StyledDocument` (paragraphs, headings, lists, links, emphasis, quotes, simple tables, images). The same tree is what M3 compose will produce from markdown via `markdown_to_document`, and `fell::render::document_column` paints it. The composer is not in this crate.

Personal and conversational mail stays native. The web view is used only when a bulk signal (List-Unsubscribe, Precedence: bulk or list, or an ESP header) coincides with layout the native painter would break (presentation or nested tables, or heavy CSS). Sync stores each received message's `text/html` and `text/plain` parts as sent, plus those bulk headers, in `message_bodies` (DEFLATE-compressed, keyed like `messages`, deleted with the row). HTML is sanitized when it is rendered, not when it is stored. `messages.body_text` stays the plain text that search, snippets and embeddings read, so folder lists and the FTS index never touch bodies. `Store::message_body` reads one message's parts and is meant for the conversation view, off the UI thread. Mail synced before this table existed is queued once in `body_backfill`; the sync thread fetches it again by UID with `BODY.PEEK[]`, newest first, a few batches after each pass, and `fell_core::fetch_message_body` fetches one message on demand. Until a row has parts, `prepare_stored` on `body_text` stays native. The fixture corpus under `crates/fell-render/fixtures` locks that choice.

The web view is WebKitGTK through `wry`, dynamically linked. JavaScript is disabled and remote images are removed until the reader allows them. wry 0.57 can child-embed only into an Xlib window, and GPUI on Wayland does not provide one, so WebKit paints in an offscreen window, which is not a mapped toplevel, and the conversation shows that page in the message body. There is no second title bar and no second copy of the subject. The inbox shell toggles that with `MessageBody`; this crate does not register the keymap.

## Attachments

Sync lists every MIME part of a received message that is not its text or HTML body in `message_parts`, next to `message_bodies` and keyed the same way plus the IMAP part number (`2`, `3.1`; an attached `message/rfc822` at `2` is listed itself, then its own parts under `2.`). Each row has the type, the file name (RFC 2231 and encoded words decoded, control and bidi characters removed), the decoded and on-the-wire sizes, the transfer encoding, the Content-ID and the disposition. No bytes are stored. A part is one of three roles: an attachment, an inline image (an `image/*` whose Content-ID the HTML body loads by a `cid:` URL in `src`, `background`, `poster` or CSS `url()`, and that is not sent as `Content-Disposition: attachment`), or a signature (`application/pgp-signature`, `application/pkcs7-signature`, `application/x-pkcs7-signature`, or a part named `*.p7s` or `signature.asc`). Anything else is an attachment, wherever it sits: a file in the second slot of `multipart/signed` is not hidden. `has_attachment` and the names a forward lists come from attachments only, so a signed message or a newsletter logo is not marked. A message lists at most 256 parts. `message_bodies.parts_listed` tells an empty list from one never taken. The list follows the body rules: a resync with a body replaces it, a copy without one keeps it, `absorb_duplicate` moves it onto a kept row that has none, and an expunge saves it for undo (`local_action_parts`), including from a later copy that has files but no text. `has_attachment` and the names always describe the stored list: a write that sets the list sets them from it (which also replaces the old marker of a row stored before lists existed), and a copy whose list is not kept changes neither. Schema version 5 queues every message without a list in `body_backfill`, so the existing backfill fetches it once more.

`Store::message_attachments` reads a message's list and `Store::part_request` gives one part with the server copies to fetch it from. `fell_core::parts::fetch_part` reads the part with `UID FETCH <uid> (UID BODY.PEEK[<section>]<offset.len>)` in 2 MB windows on a short-lived read-only session, reports progress, and refuses parts over 96 MB on the wire. A server that ignores the window sends the whole part in one reply (no `<origin>`), which is read like a body up to the 32 MB literal cap; the loop also stops once the listed encoded size is in. It also refuses a copy whose part has another size than the one listed, since a merged copy may number its parts differently. It then undoes base64 or quoted-printable and writes the bytes to `$XDG_CACHE_HOME/fell/parts` (else `~/.cache/fell/parts`): directories 0700, created without following symlinks, one per part named by a hash of account, message and section, each holding one 0600 file whose name is the part's name after `parts::sanitize_filename`. A hit marks the entry used; a cached file of another size than the part's is removed and fetched again. Past 1 GB the least recently used entries are removed. `PartFetcher` runs these fetches on its own thread with its own connection, so the window never waits and a sync pass is not held up. Each `fetch` returns a `PartJob` that can be cancelled: a queued job never connects, and a running one stops after its current window and closes its session. Dropping the fetcher cancels every job and joins the thread. `prefetch_inline_parts` fetches the `cid:` images of a message that opens. Nothing follows a `Content-Location`, and nothing in core opens or runs a fetched file. `fell-mcp`'s `read_thread` reports each attachment's name, type and size, never its bytes.
