Exact-build key-to-frame
  The #125 seed tool made the separate app measurement store with 100,000
  messages in 19,240 threads. The release app ran on ARM64 Apple M2 under
  Weston 15.0.1 on private Xvfb. GPUI used Mesa lavapipe and Weston used Pixman.
  The nested hardware attempt failed with ERROR_SURFACE_LOST_KHR. Its output
  is in asahi/perf/app.log.

  FrameLog measures from the first delivered key handler to that frame's
  final paint, including time waiting for the frame. It does not measure
  keyboard hardware, GPU submission, or display presentation. The actor
  reports the actual Store::search start and end on the same clock.
  An overlapping sample is one whose key handler starts within such an
  interval. The paced run used XTEST at 47 ms per event, alternating Space
  and Backspace on invoice and then in:INBOX. This generated 417 key frames
  including navigation and query entry, 233 completed query intervals, and
  199 frames that started with query work in flight.

  Paced in-flight key-to-paint p50 0.449 ms, p95 1.037 ms, max 11.857 ms.
  Three of those 199 samples exceeded 8 ms. All 64 keyword-phase overlap
  samples were below 8 ms, with p95 1.037 ms and max 1.144 ms.
  In-flight frame build/layout/paint p95 was 0.974 ms.
  Xdotool burst replays on the same test setup measured 11.364 ms p95
  (25 overlaps, quiet host) and 20.792 ms p95 (38 overlaps, concurrent tests).
  Those runs show the effect of input timing and load on this measurement.
  The strict per-key 8 ms condition was not universal in this environment.

  Raw samples are in perf-paced/frames.jsonl, perf-software/frames.jsonl
  and perf-software-contended/frames.jsonl. frame-stats.txt holds the full
  summary. The capture and analysis scripts are in the parent directory.
